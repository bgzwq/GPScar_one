### 3.3 `Drive/Source/delay.c`　3 052 B → 4 082 B

```c
void Delay_Init(void)
{
    Timer_Init();        /* SysTick 归 RTOS，这里只保证 TIM2 时基就绪 */
}

void Delay_ms(uint32_t nTime)
{
    if (nTime == 0) return;

    /* 调度器运行中且不在中断里 -> 让出 CPU */
    if (xTaskGetSchedulerState() == taskSCHEDULER_RUNNING && __get_IPSR() == 0)
    {
        vTaskDelay(pdMS_TO_TICKS(nTime));
        return;
    }

    /* 启动阶段或中断里 -> TIM2 忙等 */
    start = Get_Us();
    while ((uint32_t)(Get_Us() - start) < (nTime * 1000u)) { }
}
```

`NB_DelayReset/NB_DelayMs/NB_DelayUs`（基于 TIM2 的非阻塞延时）**原样保留**。
`Delay_us()` 在 `timer.c` 里，基于 TIM2，**完全没动**。

## 四、三个关键设计决策（以及为什么这样取舍）

### 决策 1：**一个应用任务 + 一个心跳任务**，而不是立刻拆成 5 个任务

你原来的 `while(1)` 里，`g_mode`、`g_speed`、`g_servoAngle`、`g_mpu`、`g_distFixed/g_distRadar`、K230 环形缓冲、FatFs 句柄这些东西被反复读写。如果一次拆成 4~5 个任务：

- `menu.c` 的 KEY3 会写 `g_mode` 并调用 `Car_Stop()`，同时 `ControlTask` 正在写电机 → **控制权竞争**；
- `navlog.c` 和 `menu.c` 都会调 FatFs → **文件系统损坏**（`FF_FS_REENTRANT=0`）；
- 7 个文件都在 `printf` → 输出劈断；
- `g_mpu` 是 60 字节结构体，跨任务读写会读到"半新半旧"的值。

这些都需要重新设计"谁拥有底盘控制权"，属于架构改动，不是兼容修复。

**所以这次只做"地基"**：RTOS 真的跑起来（tick、调度器、任务、阻塞让出 CPU），业务逻辑仍单线程。
好处是：**你现有代码的时序与裸机版本逐条对得上，不需要重新验证业务逻辑**；坏处是 RTOS 的并行能力暂时没用上。

拆任务请作为独立一步，按第九节的清单来。

### 决策 2：`Delay_ms()` 用"双路径"而不是去改 12 处调用

12 处调用点分散在 `main.c:502`、`buzzer.c:128`、`key.c:55`、`location.c:137`、`menu.c:127` 等。逐个改成 `vTaskDelay` 意味着：

- 要判断每一处是不是在中断里（`Buzzer_Beep` 可能被别处调用）；
- 要处理"调度器启动前"的场景（`Location_Init()` 的 0.6 s 调零就在 `BSP_Init()` 里，**早于** `vTaskStartScheduler()`）。

双路径把这两个判断收在一个函数里，**调用方一行都不用改**，风险最小。

### 决策 3：FatFs 故意保持 `FF_FS_REENTRANT = 0`

既然所有 SD 访问都在 `AppTask` 里，那就没有并发，`FF_FS_REENTRANT=1` 只会增加开销和一批必须实现的钩子函数。
**保持 0 是当前结构的正确选择**，不是遗漏。将来拆任务时按第九节开。

## 五、与裸机版本的行为差异（需要你心里有数）

| 项目 | 改前（裸机） | 改后（RTOS） | 实际影响 |
|---|---|---|---|
| SysTick 归属 | 用户自己的 1 ms 计数 | FreeRTOS tick（`configTICK_RATE_HZ=1000`，仍是 1 ms） | `Delay_ms` 精度不变 |
| `Delay_ms` 实现 | 纯忙等 | 任务中 `vTaskDelay`，启动阶段忙等 | 延时变成"至少 n 个 tick"，误差 ≤1 ms；**CPU 不再被独占** |
| 主循环节拍 | 满速空转（可达几十 kHz） | 每轮 `vTaskDelay(1)`，约 1 kHz | 20/50/100/300/500 ms 的周期判定仍用 `Get_Ms()`，**完全不变**；通信轮询从"尽力快"降到 1 kHz —— 但所有串口都是中断/DMA 收进缓冲，1 kHz 取数据绰绰有余 |
| LED 心跳 | 主循环里翻 PC13 | 独立 `LedTask`，`vTaskDelayUntil` | 即使 `AppTask` 卡在超声波 30 ms 超时里，灯照样 500 ms 跳一次 |
| `printf` | 直接发字节 | 先取互斥量 | 每条多几十条指令；9600 波特率下瓶颈仍是串口本身（60 字符≈60 ms） |
| 上电 0.6 s 调零 | 忙等 | 仍在调度器启动前，走忙等分支 | **行为完全相同**（这点很重要，静止调零的判定不受影响） |
| 开机画面 `Delay_ms(800)` | 忙等 | 同上，走忙等分支 | 相同 |
| 外设 ISR 优先级 | 1~3（高于 syscall 边界） | 5~7（低于边界） | 这些 ISR 现在会被内核临界区**短暂**屏蔽（微秒级）。9600 波特率下 1 字节约 1 ms，完全无影响 |
| RAM | 25.8 KB | 61.9 KB | 增加的主要是 36 KB RTOS 堆 |
| 断言失败 | `printf` 报错（可能死等） | 关中断死循环，调试器断点可停 | 更好用，见第八节 |

## 八、调试提示（新增的钩子怎么用）

| 现象 | 现在的表现 | 怎么查 |
|---|---|---|
| 某个任务栈溢出 | 进 `vApplicationStackOverflowHook`，记录任务名到 `g_stackOverflowTask` 后死循环（**故意不 printf**，此时栈已不可信） | 调试器里全速跑，触发后 watch `g_stackOverflowTask` 指向的字符串；回到 `xTaskCreate` 把对应栈调大 |
| 堆不够（任务/队列创建失败） | 进 `vApplicationMallocFailedHook`，串口打印 `[RTOS] MALLOC FAILED` 后死循环 | 调大 `configTOTAL_HEAP_SIZE`（现 36 KB）或减少任务 |
| `configASSERT` 触发 | 进 `vAssertCalled()`，`__disable_irq()` 后死循环 | 在 `vAssertCalled` 第一行下断点，看 `pcFile` / `ulLine` |
| 想知道任务栈还剩多少 | 未使用 | 在任意任务里调 `uxTaskGetStackHighWaterMark(NULL)`，返回值是历史最小剩余（word），据此调 `APP_TASK_STACK` |

## 九、下一步：真要拆多任务时怎么办（配方，不是现在做）

如果以后要把 `AppTask` 拆开，建议顺序如下，**每一步单独验证**：

### 9.1 先加保护，再拆

| 共享资源 | 保护手段 |
|---|---|
| `printf` | 已经用 `s_dbgMutex` 保护了，`fputc` 天然安全，无需再改 |
| FatFs / SD 卡 | **二选一**：<br>①（推荐）把所有 `f_open/f_write/f_sync` 收敛到一个 `LogTask`，其它任务用队列发"写一条记录"的请求；<br>② 把 `ffconf.h` 的 `FF_FS_REENTRANT` 改 1，并在 `ffsystem.c` 里实现 `ff_mutex_create/take/give/delete`（用 `xSemaphoreCreateMutex`）；这样才需要 `configUSE_MUTEXES=1`（**已打开**） |
| LCD（SPI3） | 只有 UI 任务碰，天然安全；若两个任务都要刷屏，加一个独立的 `s_lcdMutex` |
| `g_mode` | 32 位对齐写是原子的，但"切模式 + 停车 + 通知 K230"这套**不是原子操作** → 用 `taskENTER_CRITICAL()` 包住，或规定只有 `ControlTask` 能写 |
| `g_mpu`（60 字节结构体） | 跨任务读会撕裂。用互斥量，或双缓冲 + 序号 |
| `g_distFixed` / `g_distRadar` / `g_servoAngle` | 单个 32 位 float，写原子；显示用可容忍 |
| K230 环形缓冲 | `s_rxWr/s_rxRd` 是 ISR/任务各写一个的单生产者单消费者结构，uint8_t 写原子，**现状已安全** |

### 9.2 推荐的任务划分

| 任务 | 优先级 | 栈（word） | 职责 |
|---|---|---|---|
| `ControlTask` | 4 | 256 | 20 ms 轮速刷新、电机/舵机输出、模式状态机（**唯一写电机和 `g_mode` 的地方**） |
| `SensorTask` | 3 | 320 | 超声波（100/300 ms）、MPU6050（200 ms）、ADC 读取 |
| `CommTask` | 3 | 384 | BT/ASR/K230 指令收与解析、`LanyaCon_Task` |
| `UiTask` | 2 | 512 | 按键 50 ms、LCD 300 ms、菜单、`printf` |
| `LogTask` | 1 | 768 | `Location_Update`（含 GPS 解析、0.6 s 调零）、`NavLog_Update`、FatFs |
| `LedTask` | 3 | 128 | 心跳（已有，可直接复用） |

> 优先级只作参考，关键是"**每个共享资源只有一个写者**"。

### 9.3 拆完必须复查的两件事

1. **不要在临界区里做耗时操作**（`printf`、FatFs、`Delay_ms`）。`printf` 在临界区里会导致 UART 死等。
2. **`FromISR` 只能在优先级 ≥5 的中断里调用**。现在已经全部 ≥5，可以放心用 `xQueueSendFromISR()`。

### 回滚要点

- **只回滚 `stm32f4xx_it.c` 是不够的**：必须同时把 `FreeRTOSConfig.h` 的 3 个映射去掉，否则 `port.o` 会去定义 `SVC_Handler` 而没人调用（照样能编译，但调度器起不来）。

## 十二、一句话总结

那两个 `L6200E` 只是表面症状；真正让 RTOS 跑起来要做的是**三件事**：
**把 3 个异常向量还给 `port.c`**（编译通过）、**把 SysTick 的 tick 交给内核并让 `Delay_ms` 学会让出 CPU**（跑得起来）、**把 ISR 优先级压到 syscall 边界之下 + 给 printf 加锁**（后面拆任务时才不会炸）。

这三件事都做完了，业务逻辑一行没改，`AppTask` 里还是你原来的代码。
