## 三、阻断级问题的根因（P1 / P2）

FreeRTOS 的 Cortex-M 移植层里，这三个异常处理函数**用的是 FreeRTOS 自己的名字**：

```c
// RTOS/port/RVDS/ARM_CM4F/port.c
__asm void vPortSVCHandler( void )     // :277
__asm void xPortPendSVHandler( void )  // :457
void  xPortSysTickHandler( void )      // :519
```

FreeRTOS 的约定是在 `FreeRTOSConfig.h` 里把它们 `#define` 成向量表里的名字：

```c
// MY/FreeRTOSConfig.h:303-304
#define xPortPendSVHandler 	PendSV_Handler
#define vPortSVCHandler 	SVC_Handler
// ←←← 注意：这里缺了第三行
// #define xPortSysTickHandler SysTick_Handler
```

而你的 `stm32f4xx_it.c` 里**也定义了同名的空函数**：

```c
// MY/stm32f4xx_it.c
void SVC_Handler(void)    { }   // :96
void PendSV_Handler(void) { }   // :114
void SysTick_Handler(void) { TimingDelay_Decrement(); }  // :123
```

于是 `port.o` 和 `stm32f4xx_it.o` 各自提供了一个 `SVC_Handler` / `PendSV_Handler` → **L6200E**。

> ⚠️ **关键点：`FreeRTOSConfig.h` 只映射了 2 个，第 3 个（SysTick）没映射。**
> 这意味着即使你把 SVC/PendSV 的冲突解决了，`xPortSysTickHandler` 依然是个**没人调用的孤儿函数**，`SysTick_Handler` 还是你的（只做 `TimingDelay_Decrement()`）——**FreeRTOS 的节拍永远不会前进**，这就是 P3。

启动文件 `startup_stm32f40_41xxx.s` 里这三个都是 `[WEAK] Default_Handler`，所以"删掉 `stm32f4xx_it.c` 里的空实现"这个动作本身是安全的（会自动落到 `port.o` 的强符号上）。

## 四、中断与优先级（P7 / P8）

### 4.1 NVIC 优先级分组：现状是"碰巧对"，但随时会被踩坏

`FreeRTOSConfig.h` 假设 **4 位全部用作抢占优先级**：

```c
configLIBRARY_LOWEST_INTERRUPT_PRIORITY        15    // :290
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY    5    // :293
configKERNEL_INTERRUPT_PRIORITY  = 15 << 4 = 0xF0    // :295
configMAX_SYSCALL_INTERRUPT_PRIORITY = 5 << 4 = 0x50 // :297
```

全工程**没有任何一处** `NVIC_PriorityGroupConfig()`。Cortex-M4 复位后 `SCB->AIRCR.PRIGROUP = 0`，即 4 位全抢占 —— 和 FreeRTOS 的要求一致，**所以现在是对的**。

但是：
- 绝大多数 STM32 例程/教程都会在 `main()` 开头写一句 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_2);`（2 位抢占 + 2 位子优先级）。**一旦有人加上这句，FreeRTOS 的临界区和 `BASEPRI` 机制立刻错位，表现为随机死机/丢中断，而且极难查。**
- 反过来，你现有驱动的 `SubPriority` 现在全部**无效**（4 位全抢占时没有子优先级位），写多少都不起作用。

建议（待你决定）：显式写一句 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4);` 锁死分组，比依赖复位值安全。

### 4.2 现有全部中断及其优先级

| 中断 | 使能位置 | 抢占 / 子 | 逻辑优先级 | 能不能调 FromISR API？ |
|---|---|---|---|---|
| `TIM1_TRG_COM_TIM11_IRQn`（蜂鸣器翻 IO） | `buzzer.c:59-62` | 2 / 2 | **高于 5** | ❌ 不能 |
| `USART3_IRQn`（ASRPRO） | `asrpro.c:69-72` | 1 / 2 | **高于 5** | ❌ 不能 |
| `USART2_IRQn`（蓝牙） | `bluetooth.c:70-73` | 1 / 1 | **高于 5** | ❌ 不能 |
| `USART6_IRQn`（GPS 空闲中断） | `gps.c:338-341` | 2 / 2 | **高于 5** | ❌ 不能 |
| `USART1_IRQn`（K230） | `K230.c:128-131` | 3 / 0 | **高于 5** | ❌ 不能 |
| `SDIO_IRQn` | `FatFs/sdio_sd.c:580-583` | 1 / 0 | **高于 5** | ❌ 不能 |
| `DMA2_Stream3_IRQn` | `FatFs/sdio_sd.c:586-588` | 1 / — | **高于 5** | ❌ 不能 |
| `SysTick` | `delay.c:24` / `port.c:701` | 15 / — | 最低 | （内核自己用） |

**规则**：`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5` 的含义是——**只有数值 ≥ 5 的中断（即逻辑上"更低优先级"）才被 `BASEPRI` 屏蔽，才允许调用 `...FromISR()` 系列 API**。你现在所有 ISR 都在 1~3，全部处于"不受内核管辖"的高优先级区。

现状下这些 ISR 都只做裸机的事（存字节、置标志），所以暂时不违规。但只要你打算：
- 在 UART ISR 里 `xQueueSendFromISR()` 把收到的字节交给任务；
- 在超声波/定时器 ISR 里 `xSemaphoreGiveFromISR()` 唤醒任务；

就**必须把这些中断的抢占优先级改成 ≥5**（比如 5、6、7），否则 `portASSERT_IF_INTERRUPT_PRIORITY_INVALID()` 会立刻断言（断言又会走 `printf` → 见 P17，表现为莫名卡死）。

顺便提醒：GPS 那条用的是 **DMA2_Stream2 + USART6 空闲中断**，`sdio_sd.c` 用的是 **DMA2_Stream3**，两者不冲突，但修改优先级时不要只改 UART 忘了 DMA。

## 五、内存与栈（P9）

### 5.1 现有 RAM 预算

| 项目 | 大小 | 说明 |
|---|---|---|
| 当前 RW + ZI（改动说明.md 记录） | 约 25.8 KB | 裸机版本 |
| `configTOTAL_HEAP_SIZE` | **36 KB**（`FreeRTOSConfig.h:187`） | `heap_4.c` 的 `ucHeap[]` 静态数组，全部计入 ZI |
| 合计 | 约 62 KB / 128 KB | 还有余量，但**没算任务栈之外的其它开销**（队列、TCB 都从这 36KB 里出） |

`STM32F407ZGT6` 的 SRAM 是 112KB(SRAM1) + 16KB(SRAM2) 连续 128KB，够用。但要注意：
- `heap_4` 的 36KB 是**内核堆**，和 C 库的 `Heap_Size 0x200`（`startup_stm32f40_41xxx.s`，512 字节，给 `malloc`/MicroLIB 用）是两套东西，别互相搞混。
- 分配失败时 `configUSE_MALLOC_FAILED_HOOK = 0`（`:218`）→ **静默返回 NULL**，任务创建失败你根本看不出来。调试阶段建议改成 1。

### 5.2 栈

| 栈 | 现值 | 评价 |
|---|---|---|
| 主栈 MSP（`Stack_Size`） | `0x1000` = 4 KB | 中断和调度器启动前跑在 MSP 上，4KB 尚可 |
| `configMINIMAL_STACK_SIZE` | 128 word = **512 字节** | **太小**。Cortex-M4F 一次异常入栈就要 ~100 字节（含 FPU 上下文），再调个函数就没了 |
| 每个任务栈 | 尚无任务 | 见下 |

**实测参考**：`改动说明.md` 里用 `--info=stack` 量过最深调用链（`main → Menu_KeyProcess → Menu_MapSave → MapView_SaveToSd → NavLog_WriteBmp1bpp → f_open → … → DMA_DeInit`）= **1780 字节**。

所以任务栈建议（按功能给，单位 word）：

| 任务类型 | 建议 `usStackDepth` | 说明 |
|---|---|---|
| 纯逻辑/轮询（如按键扫描、心跳） | 128~192 | 不调 printf、不碰 FatFs |
| 串口协议解析（GPS NMEA 解析用 `double`） | 256 | NMEA 解析里用了 double 中间量 |
| LCD 刷新（调 printf、字体表） | 384~512 | 字体/图片指针操作多 |
| **FatFs / SD 卡** | **512（2KB）起** | 1780 字节那条链全在任务栈上；LFN(`FF_USE_LFN=2`) 是栈上缓冲 |

⚠️ 千万别照抄网上的 `128`。栈溢出检测现在是关的（`configCHECK_FOR_STACK_OVERFLOW = 0`，`:224`），溢出不会报错，只会表现为"莫名其妙跑飞"。

## 六、线程安全（P11 / P12）

### 6.1 `printf` → `fputc` 是单例，非重入

`Drive/Source/usart.c:74-81` 把 `fputc` 重定向到 **USART1**，而且是死等发送完成。调用 `printf` 的文件：

| 文件 | `printf` 调用处数 |
|---|---|
| `MY/main.c` | 10 |
| `Mid/Src/menu.c` | 12 |
| `Mid/Src/navlog.c` | 11 |
| `Drive/Source/lcd_spi_154.c` | 4 |
| `Program/Source/K230.c` | 4 |
| `Mid/Src/location.c` | 3 |
| `Mid/Src/mapview.c` | 2 |

一旦这些逻辑分散到两个以上任务，`printf` 会：
1. 互相打断 → 一行日志被劈成两半（**不影响功能，但调试时会被误导**）；
2. MicroLIB 的 `printf` 内部有静态状态 → 重入可能直接跑飞；
3. `while (TXE == RESET)` 在 9600 波特率下打一条 60 字符的日志要 **~60ms**，等于这个任务独占 CPU 60ms（虽然会被抢占，但延迟会累积）。

**更麻烦的一层**：USART1 同时是 K230 的数据口（见第 8 节的"老版引脚配置"结论）。如果 K230 解析任务和日志打印任务并发写 USART1，K230 会收到交错的数据帧。虽然 K230 侧靠 `0xAA+CMD+LEN+CHK` 找帧能容忍，但 TX 方向是多任务共享的，必须串行化。

### 6.2 FatFs 完全没有重入保护

```
FatFs/ffconf.h:  #define FF_FS_REENTRANT  0
                 #define FF_FS_TIMEOUT    1000
```
`navlog.c`（写 TRACK.CSV / MAP.BMP）和 `mapview.c`、`menu.c`（按键保存地图）都会碰 SD 卡。**在两个任务里同时调 `f_open`/`f_write` 会直接破坏 FAT 表**。

三条出路（待你选）：
- **A**：SD 卡操作全部收敛到**一个任务**，其它任务用队列发"写一条记录"的请求（改动最小、最稳）；
- **B**：`FF_FS_REENTRANT = 1` + 在 `ffsystem.c` 里实现 `ff_mutex_create/take/give`（需要 `configUSE_MUTEXES = 1`，见 P10）；
- **C**：不用 RTOS 时那样继续单线程，不拆 SD 相关代码。

### 6.3 共享全局状态（拆任务后必须处理）

以下全局量现在被"主循环 + 多个模块"读写，拆成任务后就是数据竞争：

| 变量 | 定义 | 读写方 |
|---|---|---|
| `g_mode` | `main.c:105` | `main.c`（模式任务）、`menu.c`、`K230.c`、`lanyacon.c` |
| `g_speed` | `main.c:106` | `main.c`、`menu.c` |
| `g_servoAngle` | `main.c:110` | `main.c`（避障/雷达） |
| `g_mpu` | `main.c:111` | `main.c` 写、`menu.c`/`location.c` 读（**结构体，非原子**） |
| `g_distFixed` / `g_distRadar` | `main.c:108-109` | `main.c` 写、`menu.c` 读（float，非原子） |
| `K230_arr[]` 环形缓冲 | `K230.c:54` | ISR 写、任务读（**已经是生产者-消费者**，只是没加保护） |
| LanyaCon 遥控数据 | `lanyacon.c` | ISR 写、任务读 |

其中 `g_mpu`（结构体约 60 字节）和 `float` 变量的读写**不是原子操作**，被抢占时可能读到"一半新一半旧"的值。

## 八、必须"改造成非阻塞"的地方（P13）

这些是裸机时代为了简单写的死等，拆任务后它们不会"卡住整机"，但会**卡住所在任务**，造成该任务周期抖动。列全给你，方便你决定哪些放进任务、哪些留在 ISR：

| 位置 | 阻塞内容 | 最坏耗时 |
|---|---|---|
| `Drive/Source/delay.c:42-47` | `Delay_ms()`：`while(TimingDelay != 0)` | 调用者指定，可达数百 ms |
| `Drive/Source/key.c:58` | `while(GPIO_ReadInputDataBit(...) == 0)` 等松手（**按键卡住就永久死循环**） | 无限 |
| `Drive/Source/ultrasonic.c:92,99` | 等 ECHO 上升/下降沿 | 每次 30ms 超时 |
| `Drive/Source/usart.c:78` | `fputc` 等 TXE | 每字节 ~1ms @9600 |
| `Program/Source/asrpro.c:172` / `bluetooth.c:177` / `gps.c:446` / `K230.c:179` | 各串口发送等 TXE | 同上 |
| `Mid/Src/navlog.c` | FatFs `f_write`/`f_sync`/`f_open`（写卡可能有几十~几百 ms） | 数百 ms |
| `Drive/Source/lcd_spi_154.c` | LCD 全屏刷新 + `LCD_Delay()` 空循环 | 数十 ms |
| `Drive/Source/mpu6050.c:163` | `Delay_us(100000)` = 100ms 忙等（只在初始化时） | 100ms |
| `Mid/Src/location.c:137` | `Delay_ms(5)` × 120 次 = 0.6s 静止调零 | 0.6s（最长 1.8s，有重试） |
| `Mid/Src/menu.c:127` | `Delay_ms(800)` 开机画面 | 0.8s |
| `MY/main.c:502` | `Delay_ms(15)`（雷达模式等舵机稳定） | 15ms |
| `Drive/Source/buzzer.c:128` | `Buzzer_Beep()` 内部 `Delay_ms(ms)` | 调用者指定 |

其中 **`key.c` 那个 `while(等松手)` 是最高危的**：它不只卡任务，是"按键被卡住/引脚短路 → 永久死循环"。而且顺带说一句：**`KEY_Init()` 全工程从未被调用**（上次分析已确认），所以这段代码实际是死代码，但文件还编在工程里。

## 十、三条路线的取舍建议（我不替你决定）

### 路线 0：暂时不接入（保持裸机）

- **做法**：把 `[RTOS/src]`、`[RTOS/port]` 两个分组从工程移除（或 exclude from build），删掉 include 路径里的 RTOS 项。`FreeRTOSConfig.h` 留着不碍事。
- **收益**：立刻恢复 0 错误；不用处理下面任何一条。
- **代价**：RTOS 的事以后还得重来一遍。
- **适合**：你目前对"任务怎么划分"还没想清楚。

### 路线 1：只打通地基，代码结构完全不动（**推荐的过渡态**）

- **要动的最小集合**（4 处）：
  1. 删掉 `stm32f4xx_it.c` 的 `SVC_Handler`/`PendSV_Handler` 空函数（解决 P1/P2）；
  2. 决定 SysTick 归属（P3/P4），**必须二选一**；
  3. 在 `main()` 里建 1 个测试任务 + `vTaskStartScheduler()`（P5）；
  4. 显式 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4)`（P7 加固）。
- **代价**：RTOS 只跑一个空任务，白占 36KB 堆；但**地基通了**，后面拆任务就是增量改动。
- **风险最低**，出问题也最容易回退。

**其中 SysTick 的二选一，是两个不同世界**：

| 方案 | 做法 | 后果 |
|---|---|---|
| **1a：SysTick 归 RTOS** | 加 `#define xPortSysTickHandler SysTick_Handler`，删掉 `it.c` 里的 `SysTick_Handler` | `Delay_ms()` **永久卡死**（`TimingDelay` 不再递减）→ 必须同时把 12 处 `Delay_ms` 改成 `vTaskDelay` 或改用 TIM2 时基（`timer.c` 的 `Get_Us/Get_Ms` 已经现成） |
| **1b：SysTick 留给 Delay** | 保持现状，`xPortSysTickHandler` 继续当孤儿 | RTOS **没有节拍**：`vTaskDelay`/延时/时间片全废，只能用"纯优先级的抢占式调度 + 同步对象" → 实际上等于没接 RTOS |

**结论：想真用 RTOS，只有 1a 一条路，`Delay_ms` 必须处理。** 好消息是 `Delay_us`（`timer.c`，基于 TIM2）**和 SysTick 无关，可以完全不动**。

### 路线 2：保守任务化（ISR 保持裸机，任务只做业务）

- ISR 里只存字节/置标志（**保持现在的写法不变**），不加任何 `FromISR` API → 那 P8 的优先级问题可以**暂时不碰**。
- 任务划分建议（按你现在的数据流）：
  | 任务 | 职责 | 栈 | 优先级 |
  |---|---|---|---|
  | `CommTask` | 串口收字节轮询 + 协议解析（BT/ASR/GPS/K230 可合可拆） | 256 | 中 |
  | `ControlTask` | 模式状态机、电机/舵机输出、20ms 轮速刷新 | 192 | 高 |
  | `SensorTask` | 超声波 100/300ms、MPU6050 200ms、ADC | 192 | 中 |
  | `UiTask` | 按键 50ms、LCD 300ms、菜单 | 384 | 低 |
  | `LogTask` | GPS 融合定位（0.6s 调零）、FatFs 写卡 | 512 | 低 |
- **printf、FatFs、SD 全部收敛到 `UiTask`+`LogTask` 两条"慢任务"，并保证任意时刻只有一个任务调 FatFs**（解决 P11/P12 的最小代价方案）。
- 全局量（`g_mode` 等）用临界区（`taskENTER_CRITICAL`）或干脆只由 `ControlTask` 独占写。
- **工作量中等，风险可控**，是最适合你现在代码形态的路线。

### 路线 3：彻底任务化 + FromISR 化

- 额外要做：重排全部中断优先级到 ≥5（4.2 表），UART ISR 改成 `xQueueSendFromISR`，`configUSE_MUTEXES=1`，为 printf/SPI/FatFs 加互斥量，开栈溢出检测和 malloc 失败钩子。
- 收益：最规范、延迟最低。
- 代价：工作量最大，且**中断优先级一改，你原来靠"高优先级 ISR 立刻响应"的行为会变**（GPS 空闲中断、SDIO 都可能受影响，需要重新验证通信不丢字节）。
- 建议：**先走路线 2 跑稳，再逐条升级到 3。**

## 十一、如果你决定动手，建议的验证顺序

1. 只解决 P1/P2 → 编译 0 error，**但不启动调度器**，烧进去确认裸机功能全部照旧（这一步确保你没改坏原来的东西）。
2. 加 `vTaskStartScheduler()` + 1 个空任务（路线 1）→ 确认程序能进任务、`printf` 能输出。
3. 在空任务里 `vTaskDelay(1000)` + 翻转 LED（PC13）→ 确认 **P3 的 SysTick 真的通了**（LED 1Hz 闪）。
4. 把 `Delay_ms` 全部替换/兼容掉 → 确认 `location.c` 的 0.6s 调零、`menu.c` 的 800ms 开机画面都正常。
5. 再开始真正拆任务，一次拆一个，每拆一个都要回归：电机转、编码器读数、GPS 有定位、SD 能写、LCD 能刷、语音/蓝牙能控。

**最容易漏的一步是第 3 步**：很多人在第 2 步就以为成功了，结果一直到 `vTaskDelay` 不返回才发现节拍没通。

## 十三、需要你拍板的 7 个决定

1. **走哪条路线**（0 / 1 / 2 / 3）？
2. **SysTick 归谁**——如果要真用 RTOS，只能是"归 RTOS + 改造 `Delay_ms`"。你倾向 `vTaskDelay` 还是继续用 TIM2 时基？
3. **`Delay_ms` 的 12 处调用**（`main.c:502`、`buzzer.c:128`、`key.c:55`、`location.c:137`、`menu.c:127`）是否接受改成非阻塞/`vTaskDelay`？特别是 `location.c` 的 0.6s 调零和 `menu.c` 的 800ms 开机画面。
4. **printf 怎么办**：加互斥量 / 收敛到单一任务 / 干脆关掉大部分日志？
5. **FatFs 怎么办**：单任务收敛（A）/ 开 `FF_FS_REENTRANT` + 互斥量（B）？
6. **`configUSE_MUTEXES` 开不开**（0 的话上面 4、5 两条都做不了）？
7. **中断优先级要不要重排到 ≥5**（决定 ISR 里能不能用 `FromISR`，也决定改动风险大小）？

你定了方向之后我再动手改，现在代码保持原样。
